      What is implemented

      Local-first security tools, with clear limits

      Core scanning and security history are designed to stay on the device. Coverage depends on Android permissions, accessible files, trusted definitions and device-specific background limits.

      On-device APK inspection

      Inspects accessible APKs and user-selected files locally, records scan history on-device, and exposes evidence behind advisory risk findings. Android does not grant an app unrestricted access to every private area or every installed app's data.

      Static threat indicators

      A bundled Kotlin engine checks DEX content against a bounded subset of YARA-compatible rules. The five-rule pack is limited—not full YARA—and matches are advisory SUSPICIOUS indicators unless independently verified evidence supports a confirmed verdict.

      Device posture review

      Reviews available Accessibility services, Device Administrator privileges, notification listeners, overlay permissions, install sources and permission-risk combinations. These are risk signals, not proof that an app is spyware.

      Monitoring & incident response

      Optional folder and install monitoring can trigger local checks, security notifications and a short alarm for qualifying indicators. Android notification/full-screen permissions, process state and OEM background rules can limit delivery; the app does not silently uninstall apps.

      User-controlled quarantine

      Quarantine uses app-private encrypted storage where supported, with guided restore and user-controlled removal. Original files are not silently deleted. Physical-device and storage-provider behavior still needs testing.

      Privacy-first core

      APK contents, scan hashes, verdicts and device-posture snapshots are not uploaded to a developer-operated server. Optional threat/model downloads use GitHub services; user-initiated Pro purchases use Google Play Billing.

      Continuous improvement · ML research

      A separate training pipeline for better candidates

      SafeMobile's companion ML repository trains and exports a compact TensorFlow Lite research model using a frozen 215-feature Drebin schema. The pipeline can accept controlled, pre-extracted feature rows from the app project's research workflow, remove duplicates and holdout overlap, and test each candidate against the same fixed holdout before publishing a new model version.

      This is repository-side research—not cloud scanning of users' phones. The installed app does not send personal APKs, scan results or device data to the training repository.

      Transparent validation status Latest documented benchmark · 31 October 2026

      The current benchmark does not yet demonstrate effective malware detection

      The measured emulator run scanned 200 APKs: 100 malicious-source samples and 100 benign samples. It recorded 0.0% confirmed-detection TPR, 0.0% FPR, 12.0% / 8.0% advisory triage TPR/FPR, and an average scan time of about 4.1 seconds per APK. The research ML model scored zero samples in that run. Source labels are not independently adjudicated ground truth.

      These results apply only to that test corpus and build; they are not certification. SafeMobile is still under validation and should not be relied on as the sole protection for a device.

      Signed threat-intelligence updates

      A separate owner-gated workflow publishes SHA-256-only indicator bundles. SafeMobile verifies the Ed25519 signature and database version before activation; the engine stays inactive when a trusted public key or valid signed bundle is unavailable. A hash match is a review indicator, not independent proof of malware.
